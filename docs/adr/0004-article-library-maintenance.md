# 文章库的删除与改名标记：随包导入每次启动都会重跑

2026-11-19。随包语料在每次启动与「重新导入」时都会按清单再对一遍，而 `docs/corpus` 里的 63 篇 id 是固定的。用户删除一篇随包文章、或给一篇随包文章改名，如果只改 `article` 表，下次启动导入就会把文章导回来、把名字写回清单里的篇名。因此这两件事各自需要一条内部标记，与业务数据放在同一笔事务里写。

## 内部标记

都存在 `setting` 表，键名与结构如下；不新增表、不改 schema 版本。

| 键 | 值 | 写入时机 |
| --- | --- | --- |
| `library.deleted-articles` | 文章 id 的 JSON 数组，升序 | 删除文章的事务里 |
| `library.title-overrides` | 文章 id → 用户篇名的 JSON 对象 | 重命名文章的事务里 |

- 语料导入只按 `library.deleted-articles` 跳过被删的随包文章；生成文章不走这条导入，不需要墓碑。
- 语料内容哈希变化、导入重写文章元信息时，篇名取 `library.title-overrides` 里的值，没有才用清单篇名。
- 删除文章时同时清掉它的篇名覆盖，避免两个标记各留一份；墓碑不清理：清理后下次导入会按清单把文章导回来。
- 两个标记都随整库备份与恢复一起走（备份是数据库快照，`setting` 表包含在内）。从备份恢复后，被删的随包文章仍不会复活，改过的名字仍在。

## 不做什么

- **不加 schema 版本**：标记只借 `setting` 表，迁移仍是 v1–11。
- **不为将来的生成文章预留额外标记**：生成文章不经过随包导入，当前的删除/改名路径已经够用；等真有另一条导入路径再加。
- 不把墓碑当成「回收站」：删除即真删，标记只服务于「别被下次导入带回来」，界面不展示、不提供恢复。

## Consequences

- 随包文章删掉后，即使换一版语料或重新安装语料文件，也不会再出现；要恢复只能重新导入到一份干净的库。
- 标记会随使用缓慢增长（每条被删的随包 id、每次改过的篇名），但只影响 `setting` 的两行 JSON，与文章体量无关。
- 改名与删除必须继续留在现有事务里；如果把标记写入拆出事务，会出现「库已改、标记没跟上」的半状态。
